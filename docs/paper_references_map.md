# AEOS-Bench / AEOS-Former 参考文献脉络整理

本文档整理自本地论文 `北航卫星.pdf`：

> Towards Realistic Earth-Observation Constellation Scheduling: Benchmark and Methodology

整理口径：

- 以论文参考文献列表为准，共 44 条。
- “是干什么的”主要依据文献标题、论文引用上下文和该领域常识整理。
- 这不是逐篇全文精读笔记，而是帮助理解这篇论文系统设计来源的“参考文献地图”。

## 一句话总览

这篇论文的参考文献大致服务于六件事：

1. 说明 AEOS / 对地观测星座调度为什么重要。
2. 对比已有 benchmark 为什么不够真实、不够大、不带物理仿真。
3. 回顾传统优化方法：约束规划、凸优化、启发式、遗传算法、蚁群算法。
4. 回顾神经网络方法：强化学习、图神经网络、Transformer、神经组合优化。
5. 支撑本文的仿真平台：Basilisk。
6. 说明相关星上计算、遥感、基础深度学习技术背景。

## 按主题分组

### 1. 应用背景：为什么要做对地观测星座调度

| 编号 | 文献 | 主要作用 |
|---|---|---|
| [3] | COSMO-SkyMed 星座规划与调度 | 真实遥感星座调度应用背景。 |
| [5] | Disaster Monitoring Constellation | 灾害监测星座的早期结果，说明对地观测星座有现实应用价值。 |
| [26] | CubeSat 星座灾害管理 | 说明小卫星星座可用于灾害管理。 |
| [33] | Grid Resource Management 星座模型 | 资源管理视角下的星座模型，偏系统/资源调度背景。 |

这一组文献回答的是“为什么要做对地观测星座调度”。核心原因是：地球观测需求很多，但卫星资源有限，卫星不能随便停在目标上空，也不能无限转姿态、无限耗电、无限存图和随时下传。真实系统里，一个调度器要同时决定哪颗卫星、在哪个时间窗口、拍哪个目标、是否值得消耗电量和姿态机动成本，以及拍完后是否能及时形成有用数据。

- [3] 说明真实遥感星座每天都要处理大量拍摄和下传请求，调度要考虑姿态机动、星上存储、用户配额、任务优先级和截止时间等工程约束。
- [5] 说明灾害监测场景非常依赖及时观测，例如洪水、火灾、地震后需要快速知道受灾范围和变化趋势，星座能提高覆盖频率，但必须调度才能优先服务紧急区域。
- [26] 说明多颗小卫星组成星座可以降低同一地点的重访时间，但星座只提供“观测机会”，真正把机会用在高价值任务上仍然依赖调度。
- [33] 更像资源管理类比：卫星星座本质上是一个分布式资源系统，要把有限的卫星、传感器、电池、存储和时间窗口分配给动态任务。

可以把对地观测星座调度理解成“天上的任务派单系统”：卫星是执行者，观测任务是订单，轨道决定什么时候路过目标，姿态机动决定能不能转过去，电池和存储决定能不能持续工作，任务截止时间决定错过后是否失效。调度的目标就是在这些限制下完成更多、更重要、更及时的观测任务。

#### AEOS-Bench 速查版

| 项目 | 有效内容 |
|---|---|
| 测试场景 | 每个场景是一个 `3600 s` 的动态星座调度问题，仿真步长 `1 s`；包含 `1-50` 颗卫星、`50-300` 个地面观测任务，任务持续时间 `15-60 s`，发布时间和截止时间都落在 `0-3600 s` 内。 |
| 场景状态 | 输入包括卫星轨道、姿态、电池、传感器、太阳能板、反作用轮等物理状态，以及任务位置、任务时间窗、任务持续时间和传感器需求。 |
| 调度动作 | 每个时间步给每颗卫星分配一个高层动作：`0` 表示不执行任务，非 `0` 表示选择某个任务；仿真器再把动作转成传感器开关、姿态指向、功耗和动力学更新。 |
| 有效观测 | 一秒有效观测需要同时满足：任务在 `release_time <= t <= due_time` 内，卫星对目标几何可见，传感器可用且类型匹配，任务尚未完成。 |
| 任务完成 | 任务必须在时间窗内连续有效观测达到 `duration` 才算完成；多颗卫星可以接力，但接力中间不能断秒，因为当前进度口径会在不可见时清零。 |
| 评估指标 | 主要看 `CR` 任务完成率、`PCR` 部分完成率、`WCR` 按任务持续时间加权的完成率、`TAT` 周转时间、`PC` 功耗和 `CS` 综合分数；其中 `CS` 越低越好，其余完成率越高越好。 |
| 复现注意 | 和论文表格对比时，必须保持同一测试 split、同一场景数据、同一 `3600 s / 1 s` 仿真口径、同一连续完成规则、同一 Basilisk 可见性/物理状态判断和同一指标公式。 |

| [44] | AEOS 综合任务聚类 | 针对敏捷卫星观测调度中的任务聚类问题，把空间或时间上相关的任务先聚成簇，再进行排程，以降低搜索规模并提高任务组织性。 |

这一组方法对本项目的启示可以概括成几句话：

- AEOS 调度不是普通分类任务，而是强约束组合优化问题，必须同时考虑时间窗、姿态机动、能耗、任务收益和多星冲突。
- 传统优化方法的优点是约束表达清楚，能把“能不能拍、转不转得过去、值不值得拍”写进规则或目标函数。
- 传统优化方法的短板是大规模动态场景下搜索成本高，遇到物理仿真闭环和跨场景泛化时效率不稳定。
- AEOS-Former 的约束模块可以理解为吸收传统优化的可行性判断，把显式约束变成神经网络注意力中的筛选信号。
- AEOS-Bench 的作用是提供统一、真实、可复现的测试场景，让传统启发式、强化学习和 Transformer 调度模型能在同一口径下比较。
- 后续改进可以借鉴主题 3 的思路：先分解再调度、显式估计姿态控制时间、对相近任务做聚类、支持突发任务下的动态重规划。

因此，主题 3 不是要说明“传统方法已经过时”，而是用来支撑本文定位：AEOS-Former 并不是简单套 Transformer，而是在真实物理 benchmark 上，用可学习模型快速近似传统优化长期重视的约束建模和可行调度能力。

这一组方法对本项目的启示可以概括成几句话：

- AEOS-Former 的模型路线不是凭空套 Transformer，而是承接了 Transformer、Pointer Networks 和神经组合优化对“变长任务选择”的建模能力。
- [23] 已经把 Transformer 用到卫星调度里，所以本文真正需要强调的是“约束感知 Transformer”，也就是把物理可行性和控制时间注入注意力。
- [15] 和 [18] 提醒我们，多星调度要处理卫星-任务匹配关系，可以从多智能体分配和图结构建模里吸收思路。
- [34]/[35] 和 [43] 指出后续可以扩展到观测 + 下传联合调度，或者采用“先选任务序列、再定执行时间”的两阶段结构。
- [4]、[20]、[22] 的作用偏背景：它们说明大规模数据和通用模型有价值，但对 AEOS 调度本身不是直接基线。

### 5. 仿真平台与物理建模

| 编号 | 文献 | 这篇论文主要讲什么 |
|---|---|---|
| [19] | Basilisk | 一个模块化航天动力学仿真框架，把轨道动力学、姿态控制、空间环境、飞行软件、传感器、电源和数据记录拆成可组合模块，并提供 Python 接口搭建闭环仿真。 |

Basilisk 不是一个现成的“卫星调度程序”，而是一套航天器仿真框架。它的核心思想是把复杂卫星系统拆成可组合模块，例如轨道动力学、姿态控制、反作用轮、太阳能板、电池、传感器、飞行软件和数据记录模块，再通过统一的任务调度和消息传递机制把这些模块接成一个闭环系统。这样做的好处是：研究者不需要为每个实验手写整套物理仿真，而是可以复用已有模块，并按需求替换控制器、传感器模型或电源模型。

对 AEOS-Bench 来说，Basilisk 的价值不在于“帮你自动求最优调度”，而在于“帮你判断某个调度动作在物理上是不是真的能执行”。调度器可以只输出高层决策，例如哪颗卫星在当前时刻去执行哪个任务；而 Basilisk 负责检查这条决策链条后面的真实物理条件是否满足，包括卫星当前轨道位置是否能看到目标、姿态能否及时转向、反作用轮和控制器是否稳定、电池与太阳能输入是否允许持续工作、传感器视场和状态是否满足观测要求。也就是说，AEOS-Former 决定“想怎么调度”，Basilisk 决定“这种调度到底能不能真的发生”。

因此，主题 5 对本文的作用很关键：它支撑 AEOS-Bench 的“真实物理仿真”定位，使 benchmark 不会退化成只在抽象图结构或简单几何规则上做任务分配。也正因为有 Basilisk，论文才能更有说服力地宣称自己考虑了轨道、姿态、电池、太阳能板、反作用轮和传感器等真实状态，并用闭环执行结果而不是纸面可行性来评价调度策略。这也是 AEOS-Bench 区别于很多简化 benchmark 的关键证据。

这一组文献对本项目的帮助主要有三点：

- 它们提供应用背景：AEOS 调度不是为了抽象地“完成任务数”，而是服务海事监测、空间目标跟踪、灾害响应等需要快速成像和快速处理的真实任务。
- 它们提醒我们，真实星座调度还受星上计算和通信能力影响；卫星拍到图像后，可能还要在星上做目标检测、跟踪、压缩、筛选和转发。
- 它们能支撑论文里的现实性论证：AEOS-Bench 目前重点建模轨道、姿态、电源和传感器，但未来扩展可以继续加入星上处理时延、计算功耗、存储容量、下传窗口和星间链路约束。

对当前 AEOS-Former 来说，主题 6 不是直接算法基线，而是说明“调度动作背后还有完整的星上任务链”。如果后续要把 benchmark 做得更真实，可以把任务从单纯观测扩展为“观测 + 星上处理 + 数据下传 + 星间转发”的闭环流程。

### 7. 优化器与训练基础

| 编号 | 文献 | 这篇论文主要讲什么 |
|---|---|---|
| [24] | AdamW | 论文指出在 Adam 这类自适应优化器里，传统 L2 正则化并不等价于真正的权重衰减；AdamW 把权重衰减从梯度更新中解耦出来，从而改善泛化性能并让学习率和权重衰减更容易分别调节。 |

AdamW 对本项目的作用很具体：AEOS-Former 是 Transformer 类模型，参数量较大，训练时需要稳定的自适应优化器。AdamW 能在保持 Adam 收敛速度的同时，通过解耦权重衰减减少过拟合风险，所以适合作为监督训练和迭代训练阶段的默认优化器。复现实验时，学习率、warmup、weight decay 和训练轮数都要和论文配置保持一致，否则模型收敛速度和泛化结果可能明显变化。

## 这篇论文如何站在这些文献之上

可以把 AEOS-Bench / AEOS-Former 的定位理解成：

1. 传统优化方法能处理约束，但在大规模动态场景下计算成本高。
2. 启发式和演化算法速度更快，但面对复杂物理约束和泛化场景时性能不稳。
3. 现有神经网络方法能学习调度策略，但很多 benchmark 太小、物理仿真不真实、缺少高质量标注。
4. 本文用 Basilisk 搭建更真实的物理仿真，用 AEOS-Bench 提供大规模标注，再用 AEOS-Former 把 Transformer 和显式约束模块结合起来。

所以这篇论文的核心卖点不是单纯“又提出一个 Transformer”，而是：

- benchmark 更大；
- 物理仿真更真实；
- 有专家生成的轨迹标注；
- 模型里显式加入卫星-任务可行性约束；
- 用模拟器闭环迭代提高策略质量。
